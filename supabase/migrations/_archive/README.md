# Archived migrations — divergent repo history

These 12 migrations were the repo's original migration history before the
2026-05-15 reconciliation under [ADR Decision 8](../../../docs/ARCHITECTURAL-DECISIONS.md#decision-8--migration-drift-reconciliation-path-a-production-as-baseline).

They are **not replayed** by `supabase db reset` — Supabase only loads
`*.sql` files in `supabase/migrations/` proper, not subdirectories. They
are kept here for git-blame value and as a record of the design intent
that diverged from production.

---

## Why these are archived

After six weeks of independent maintenance, the repo's migrations and
production's migrations had diverged structurally — not just in
function-signature drift, but in fundamental schema design:

| | Repo migrations (these files) | Production reality |
|---|---|---|
| Enumerated columns | 13 enum types via `CREATE TYPE … AS ENUM` | TEXT + CHECK constraints |
| Value casing | lowercase (`super_admin`, `pending`) | UPPERCASE (`SUPER_ADMIN`, `CREATED`) |
| Shipment lifecycle | 10 states (`pending`, `booked`, `manifested`…) | 11 states (`CREATED`, `PICKUP_SCHEDULED`…) |
| Role helper function | `current_user_role()` returning `user_role` enum | `get_user_role()` returning text |

`supabase db push` skips by filename — these migrations were **never
applied** to production. Replaying them on a fresh DB produced a
different schema model than production has, which is what kept the
fresh-DB CI gate red on every PR for two weeks.

The full divergence analysis is in
[supabase/snapshots/MIGRATION-DRIFT-CATALOG-2026-05-15.md](../../snapshots/MIGRATION-DRIFT-CATALOG-2026-05-15.md).

---

## Replacement

The single replacement is
[../20260515000001_baseline_from_production.sql](../20260515000001_baseline_from_production.sql) —
a consolidated baseline migration generated by introspecting production
and embedding the captured schema verbatim. On a fresh `supabase db
reset` it reproduces production exactly (including the latent
`invoice_payments_insert` 'OPERATOR' RLS bug, which is fixed in the
forward migration following the baseline).

Production's bookkeeping was updated in the same PR cycle to insert the
17 historical production filenames into
`supabase_migrations.schema_migrations` so `supabase db push` recognizes
them as already-applied. From that point forward, production and repo
migrate together via normal `supabase migration new` flow.

## Don't restore these

If you need a piece of design intent from one of these files:

1. **First check** `supabase/migrations/20260515000001_baseline_from_production.sql`
   — production has it (and so does the baseline) most of the time.
2. **If genuinely missing** — for example, a hardening pattern from
   `20260514000003` that production doesn't have yet — write a NEW
   forward migration with a fresh dated filename. Do NOT move files
   back out of this archive.

Restoring an archived file would re-trigger the divergence problem
that prompted Path A in the first place.
